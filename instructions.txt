# Build a Native iOS App: Instant English ↔ Hindi Word Explainer

## ROLE

You are a senior native iOS engineer specializing in Swift 6, SwiftUI, accessibility, and Apple's system frameworks.

Build this as a **native iOS application**, not React Native, Flutter, Expo, or a web wrapper.

Prioritize:

* Extremely fast interaction
* Minimal UI
* Native iOS behavior
* Offline-friendly operation
* Low battery usage
* Accessibility
* Simple maintainable architecture
* iPhone-first UX
* iOS 16+ compatibility

Do not over-engineer the application.

---

# 1. PRODUCT

Build a small educational utility for parents, teachers, and students who need to understand English or Hindi words instantly while studying.

### Core problem

While teaching a child, the teacher/parent may encounter a word they don't know well.

They should be able to:

> **See word → tap/share/speak → immediately understand it**

without navigating through multiple screens.

The application should work in both directions:

**English → Hindi**

and

**Hindi → English**

The app is NOT intended to be a traditional dictionary with complicated navigation.

It is an **instant word explainer for study time**.

---

# 2. PRIMARY UX PRINCIPLE

## MINIMUM INTERACTION

This is the most important product requirement.

A user should ideally need:

**1 action → result**

Examples:

### Typing

Open app → type `adapt`

Immediately show the result.

### Voice

Open app → tap microphone → say:

> "What does perseverance mean?"

Show the result.

### Share Sheet

In another application:

Select `photosynthesis`

→ Share

→ this app

→ directly show the result.

### Textbook sentence

Paste:

> Animals adapt to their environment.

The app should identify useful vocabulary and allow the user to understand the words in context.

Do NOT make users:

Search → select language → select dictionary → select result → open details.

Language should be detected automatically whenever possible.

# 9. AUTOMATIC LANGUAGE DETECTION

Do not ask:

> English or Hindi?

before every lookup.

Detect language automatically using Apple's NaturalLanguage framework and/or dictionary response characteristics.

Examples:

```text
adapt
→ English

परिस्थिति
→ Hindi

अनुकूल
→ Hindi

resilient
→ English
```

If detection is ambiguous, show a tiny non-blocking language indicator that can be changed manually.

Do not interrupt the lookup flow with a language-selection screen.

The result should appear immediately below the search field or as a very lightweight result transition.

Avoid unnecessary navigation.

# 15. CONTEXT MODE

If the user enters a sentence, do not treat it as a normal dictionary word.

Example:

```text

```

Identify:

```text

```

and understand its contextual meaning.

Show:

```text

Here it means:

the land beside a river.

नदी का किनारा
```

Provide a simple option:

**Explain sentence**

which explains the entire sentence in simple English/Hindi.

# 18. VOICE INPUT

Use Apple's Speech framework where available.

The user should be able to tap:

🎙

and speak:

> "What does perseverance mean?"

The app should extract:

```text
perseverance
```

and immediately perform the lookup.

If the user says:

> "What is the difference between affect and effect?"

recognize this as a comparison request.

Do not require the user to manually type the words.

Handle speech permission gracefully.

If permission is denied, continue supporting typing.

# 19. TEXT-TO-SPEECH

If an API provides a native pronunciation audio URL, use it where available.

Provide a fallback.

# 24. OFFLINE-FIRST BEHAVIOR

The application should cache previously searched words.

If the user previously searched:

```text

```

then searching it again should use local cached data when appropriate.

Show a subtle offline state if the network is unavailable.

Do not display a giant error page.

Example:

```text
You're offline

Showing saved dictionary information.
```

Previously cached results must remain accessible.

# 26. FREE DATA SOURCES

For the MVP, investigate and use reliable free/public dictionary resources.

Potential sources include:

* Free Dictionary API for English dictionary data

Before implementation, verify:

# 27. API FAILURE HANDLING

If the API fails:

Do not show:

```text
HTTP 500
JSON decoding failed
URLSession error
```

Show:

```text
Couldn't find that right now.

Check your connection and try again.
```

Provide:

```text
Retry
```

For cached results, prefer showing the cached result rather than failing.

---

# 28. SEARCH BEHAVIOR

Search should feel instantaneous.

Use:

* debounce where appropriate
* local cache first
* async network requests
* cancellation of obsolete searches
* loading state only when necessary

Do not send a network request for every character typed.

For example:

```text
r
re
res
resi
resil
resili
```

should NOT produce six API requests.

Search should normally execute when:

* the user submits
* the user pauses appropriately
* or a direct lookup is requested through Share/voice.

# MOST IMPORTANT PRODUCT RULE

Whenever there are two possible implementations, choose the one that requires **fewer interactions from the teacher**.

The app should disappear into the teaching workflow.

The ideal experience is:

> **See a word → get curious → one action → understand it → continue teaching.**

Do not turn this into a conventional dictionary application.

Build a **fast, quiet, context-aware English ↔ Hindi teaching companion.**
